# Playtest — M2 increment 8, the friction increment

Date: 2026-09-14 · Build: M2 increment 8 · Ship: TB-1 · Scenario: `core:spe-transit`,
seed 1553 (the same event as the 2026-09-13 session, so the two transcripts compare)

Three runs. A and B through the teletype, C through the procedure runner so the
retargeted task card and the new close-out could be read step by step. The increment
was five playtest findings from the last three sessions, so the question was not "does
it work" but "does the game play differently now".

## Run A — the wait that stops

Powered up, checked out, typed `wait 600` at MET 0:00:05 and went away.

```
> wait 600
* [    66.1s] CAUTION   SEU HAZARD RAISED
* [   341.9s] CAUTION   DATA BUS A DEGRADED RAISED
* [   341.9s] WARNING   DATA BUS A FAILED RAISED
... 337.1 s of 600 s pass. MET 000:00:05:42.0
WAIT INTERRUPTED — WARNING: DATA BUS A FAILED (262.9 s of the wait remaining; 'wait 262.9' resumes it)
```

This is the finding from three consecutive sessions, closed. The old client slept the
full ten minutes and handed back a ship that had been jammed for four and a half of
them. It now stops at the onset, names it, and tells the player what is left — the
remainder is a number they can type, so resuming is a decision and not a re-guess.

Both surfaces share one primitive (`interaction/watch.py`): the runner's wait step and
the console's `wait` cannot drift, which is the ui-presentation feature-parity contract
being enforced by construction rather than by discipline.

The caution rule reads right in play. `SEU HAZARD` at 66.1 s did not stop the clock and
should not have: the flux was climbing, there was nothing to do about it, and a wait
that stopped there would have trained the player to stop typing `wait`.

**Defect found and fixed in-session:** the first transcript printed the interruption
line *before* the event lines that caused it, because the client flushed events at the
top of the next loop pass. An operator reading "INTERRUPTED by DATA BUS A FAILED" and
only then seeing the raise is reading backwards. Events now flush before the summary
line, in time order, as the block above shows.

## Run B — working the jam

Acknowledged, then FIM 42-11 by hand: cycle CB A2 (no change, RT 12 innocent), cycle
CB E3 — bus recovers. Verdict RT 5.

The moment worth recording is the read taken while CB A2 was still open:

```
db.a: FAILED — 0/2 RTs healthy (bc bc.a)
  RT 12: NO RESPONSE — SHED (cb.a2 open)
  RT 5: NO RESPONSE
```

Two silent terminals, and the page says which silence the crew caused. The BC's own
table still reads `NO RESPONSE` against both, unannotated, as it must — the controller
does not know about breakers. The bare line is the one carrying information now: *the
ship has no innocent explanation for RT 5.* That is isolation data the player did not
have to walk the panel for, and it is not a God View, because the breaker position and
the maintenance record are both things they could read at another address.

count was not the new board's. The task now ends with the same zero-and-prove the
checkout does (steps 13–15), and NOTE 4 says to write the totals down first.

## Findings (not fixed)

1. **`sys annunciator recall` is not a verb.** ATA 31 and QRH 42-01 both use the word
   *recall* for the ordered list of lit lamps; the panel answers to `read`. The refusal
   is helpful (`try: read, ack, test`) but the manual taught a word the ship does not
   know. An alias is cheap and the vocabulary should match the book, not the other way.
2. **A wait cannot be resumed as one act.** The client says `'wait 262.9' resumes it`,
   and the player must retype it. A `wait --resume` (or just `wait` with no argument
   picking up the remainder) would make the loop a loop.
3. **Nothing in the shipped corpus waits long enough to be interrupted.** The longest
   wait in any procedure is 2 s. The feature earns its keep at the console, where the
   player types `wait 600`, and it will earn it in procedures when the thermal loop and
   burn monitoring arrive — but today the runner path is exercised only by its tests.
4. **`SOM 42-30-02` monitors with an expectation poll, not a wait**, so its "hold until
   the flux falls" step does not interrupt on a warning. The watch only covers `wait_s`
   steps. A terminal latching up under a long `within_s` poll is exactly the case §3 of
   that page warns about, and the runner will walk right past it.
5. **Removal still records no reason** (carried from increment 7), and **error counters
   are per-bus, not per-unit** — a swapped board's history does not follow it to the
   bench. Both close when the LOG notebook write verb lands.
